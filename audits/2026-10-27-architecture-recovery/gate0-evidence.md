**What the verifier found that the reader missed (security-rulesets):**

- HYPOTHESIS, highest impact. On both push and pull_request events, GitHub runs the workflow definitions from the pushed branch or PR merge ref, not main's. A same-repo branch's workflow receives every repository secret, and the repo has no environments (`gh api .../environments` returns total_count 0), so all five secrets are repo-wide. test.yml triggers on push to claude/** (line 12). Any credential that can push a claude/** branch containing .github/workflows changes therefore gets a workflow that can declare write permissions and read every secret: AGENT_LEDGER_KEY, BUILDER_APP_KEY, ANTHROPIC_API_KEY, OPENAI_API_KEY, CR_ENG_REVIEWER_TOKEN. Such a workflow can also post green test, agent-guard, agent-verify or agent-review checks through the Checks API, and all four required contexts come from integration 15368. 'AGENT_LEDGER_KEY held by no build job' is true of main's workflow text only. The App is kept out by lacking the Workflows permission (rulesets README 34-36; probe result line 45), and GITHUB_TOKEN cannot push workflow files. The Backlog routine pushes as kuaya1 with admin bypass. If that credential carries workflow scope, only the prompt stops it (routine-a.txt lines 12 and 18 forbid .github edits). backlog-pr's scope check only reports protected paths and leaves the PR open (backlog-pr.yml 9-12).
- agent-verify computes its verdict from processes the candidate controls. runTests spawns `node --test` on the candidate's files as the same user and on the same filesystem as the trusted/ checkout and $RUNNER_TEMP/task.json (agent-verify.js 113-127). It reads the exit status and TAP counts from that process. A hostile candidate can shape its own pass, so agent-verify is a quality gate, not a security boundary. This matters most for Owner-change PRs, where it is skipped anyway.
- S17 correction: backlog-promote.js admit() defaults to `push = defaultPush` (line 486) and pushes main at line 546 whenever admission runs without `--propose true`. The main-pushing path is therefore reachable from two CLI subcommands, promote and admission, not only promote.
- scout-cron.yml's checkout takes no ref (30-32), and workflow_dispatch can target any branch. Once XAI_API_KEY and DESK_INGEST_* are set, a dispatch on a model-written branch would run that branch's grok-cron.js with those secrets.
- The live main-merge-requirements also carries required_reviewers:[], and the live update rules omit update_allows_fetch_and_merge. Both are representational. The checked-in JSON and merge-boundary-check.js should be compared on semantics, not text, before relying on 'files equal live'.
- automation-branches includes ~ALL, so it also evaluates main. Rule suites for Eric's PR merges show automation-branches 'update fail' overridden by the admin 'always' bypass. On main, then, only main-merge-requirements (no bypass) actually binds. On every other branch, the admin can force-push or delete anything except agent-ledger, whose ruleset has no bypass.
- The visual-proof branch is excluded from every ruleset and holds the screenshots that PR comments embed via raw URLs. Any contents:write token can rewrite it, including the reserve, record and agent-review jobs, backlog-intake and engineering-admission. The proof images in a PR comment are therefore not tamper-evident.
- PDF claim (4), the four admitted engineering tasks with no lease, was not re-verified by the finder or here. It rests only on the orchestrator's connector snapshot.
