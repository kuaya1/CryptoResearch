# Templates

| File | What it is |
|---|---|
| `research-prompt.v1.md` | The research prompt body. `{{PLACEHOLDERS}}` are filled per project, and each project gets its own copy in `projects/<id>/prompts/`. |
| `grading-appendix.v1.md` | The grading and output appendix template. It contains the shared JSON contract every provider must return. |
| `research-prompt.v5.md`, `grading-appendix.v5.md` | **Used for new research runs.** `cr-research-prompt@5`, the position thesis prompt for any project. One decision question (is this a legitimate, well-built project whose token offers an attractive opportunity during the holding period, and what would confirm or invalidate it); a summary first; six research sections (identity and legitimacy; development, build and code quality; product reality and technology usefulness; demand, token economics and valuation; chart, volume and market cycle; independent judgment and asymmetry); bear, base and bull scenarios that keep observation, assumption and forecast apart, with unknown probabilities and price ranges allowed; thirteen category grades. The scoring profile adds its sector focus to the same six sections. The JSON contract is `cr.report.v2`. The six weighted components and their weights are unchanged. Used with the `@2` scoring profiles; a profile without a version written for it keeps `v4`. |
| `research-prompt.v4.md`, `grading-appendix.v4.md` | `cr-research-prompt@4`: the position-cycle@1 recipe plus the report contract (source types, primary evidence for critical claims, optional scenario probabilities). Kept for the runs and reports made with it. |
| `research-prompt.v3.md`, `grading-appendix.v3.md` | `cr-research-prompt@3`, the position-cycle@1 recipe: an exact calendar horizon (4 months by default; longer only as a long-term exception with your reason), the market-cycle snapshot, sections on market cycle, timing and catalysts and a review plan, and a `position_context` block in the JSON contract. Scoring is unchanged. `v2` and `v1` stay for older reports. On 2026-10-02, before any real report used v3, it gained one optional placeholder, `{{OWNER_FOCUS}}`: your instructions from a New research request, quoted as questions to investigate (never as conclusions). Without instructions it renders to nothing, so the prompt is byte for byte what it was. |
| `execution/chatgpt.v1.md` | `cr-execution-chatgpt@1`, ChatGPT's execution note (from 2026-10-03): how ChatGPT works through the research prompt (fetch it whole, research independently, judge where the evidence supports it, assess all six investment components explicitly, never fill in numbers to complete the form, explain each unknown, check the JSON block against the report). It adds no research question, scope or grading rule, and the prompt stays one text for every model. It is rendered and frozen with each new ChatGPT job (`research/<run>/execution.chatgpt.md`, its SHA-256 on the job) and delivered exactly as frozen: through the desk connection before the prompt, as the OpenAI API's `instructions` (the input stays the prompt byte for byte), or before the prompt copied by hand. Jobs made earlier have none. A change is a new file and version. |
| `execution/chatgpt.v2.md` | `cr-execution-chatgpt@2`, ChatGPT's execution note for jobs made from 2026-10-04 on: one project per request with its save receipt; primary sources before grading; one bounded retry for a failed source, then a plain disclosure; history as old as the project is; evidence, weakness, assumptions and reason per judgment; a point where supported, a range only between two named readings (a judgment, not a confidence interval), otherwise unknown; chart inputs and their limits; the JSON block checked against the schema; a withheld grade is acceptable and a re-save needs a documented reason. `@1` stays for the jobs frozen with it. |
| `appendix/grading-appendix.<profile>.v1.md` | A ready-to-use appendix for each sector profile. Append it to any prompt of your own (for example your original Huma prompt). Then set `provider`, or leave it null; the inbox folder decides. |
| `rubrics/cr-grading.v1.json` | The six investment components and their weights (20/25/20/15/10/10), the grade labels, the downside-risk panel, the scale anchors and the rules. |
| `rubrics/payfi-credit.v2.json`, `rubrics/network-infrastructure.v2.json`, `rubrics/general-token.v2.json` | **Used for new research.** The thirteen category grades (project legitimacy, development credibility, build and operational quality, code quality, live product reality, technology usefulness and defensibility, organic demand and adoption, token value capture, valuation and supply attractiveness, chart structure, cycle position and catalyst timing, volume confirmation and executable liquidity, BTC-relative asymmetric opportunity), each defined for its sector, plus that sector's focus for the six research sections and its economics fields. A project saved with an `@1` profile keeps its record; its new research uses the `@2` version of the same profile. |
| `rubrics/payfi-credit.v1.json` | The 11 diagnostic categories from the PayFi template, including credit-risk transparency, plus the 10 research sections and the economics fields. Kept for the reports that declare it. |
| `rubrics/network-infrastructure.v1.json` | For AI, DePIN, L1/L2, oracle and compute networks. Credit-risk transparency is N/A here; `technical_risk_transparency` has its own definition and is not comparable with credit scores. |
| `rubrics/general-token.v1.json` | The fallback profile. Credit is N/A; `protocol_risk_transparency` is its own dimension. |
| `schemas/*.schema.json` | JSON Schemas for reports, projects, transactions, requests, journal entries and events. `report.v2.schema.json` (`cr.report.v2`, asked for from `cr-research-prompt@5` on) adds to `report.v1.schema.json`: category grades with confidence, strongest evidence, main weakness and what would raise or lower them; the `code_review`, `chart_cycle` and `independent_judgment` blocks; scenario observations and a note for unknown price ranges. A report is checked against the schema of the format it declares; v1 is unchanged. |
| `forensics/forensic-prompt.v1.md` | `cr-forensic-prompt@1`, the Forensics & Resilience investigator prompt (Claude): does the advertised product work; are incentives, disclosures, controls and observed actions consistent; could liquidity, operations or delivery deteriorate over 120 days; what supports it and what would change it. | `source-prompts/` | Your original prompts, kept as you wrote them. |

## Versioning

Never edit a published version in place: older reports declare which version they were graded under, and their meaning must not change underneath them. To change wording, weights or categories:

1. Copy the file to the next version (for example `research-prompt.v2.md` or `payfi-credit.v2.json`).
2. Change the `@` reference inside it (for example `payfi-credit@2`).
3. Point new prompts at the new version.

Reports graded under different rubric or profile versions are shown side by side but are never compared numerically. A stored report is always read under the versions it declares, and a research run keeps the prompt it was created with, so publishing a new version changes nothing that already exists. `dashboard/tests/prompt-v5.test.js` pins the fingerprints of the published prompt templates, appendices, the v1 report schema and the grading rubric.
